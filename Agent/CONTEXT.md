# Beacon — project context (v1.0.0)

Beacon is a dead-simple, Grafana-style monitoring dashboard for homelabs: drag-and-drop grid, every tile configurable in place, built on data already collected. Reference points the author found too heavy or too light: CheckMK, Beszel, Uptime Kuma, Netdata.

## Stack and layout (flat folder)
- `app.py` — Flask + paramiko + SQLite. Threads: `loop` polls devices (from the UniFi Network API when a site is set up under Settings > UniFi, see below; otherwise over SSH, reading /proc plus `mca-dump` for UniFi extras); `sloop` pings servers (`ping` binary, own interval).
- `index.html` — whole UI: vanilla JS, Chart.js from a CDN, no build step. Sign-in splash, settings dialog, tabs, grid.
- `vendor/chart.umd.min.js` is downloaded by the Dockerfile at build time (served at `/vendor/chart.umd.min.js`; if missing the page tries the CDN, then `MiniChart`, a small built-in line chart in index.html).
- `Dockerfile` (installs iputils-ping, libcap2-bin, gosu; non-root), `entrypoint.sh`, `docker-compose.yml` (service `beacon`, cap NET_RAW), `.env.example`, `config.example.json`, `requirements.txt`.
- Runtime data in `/data`: `stats.db` (tables `samples`, `pings`), `devices.json`, `servers.json`, `dash.json`, `settings.json` (interval, server_interval, guest), `users.json`, `brand.json`, `secret.key`, `unifi.json` (the sites with their API keys, the device-check schedule and its last result, hosts removed by hand; 0600), `icons/` (cached app icons), optional `config.json`; every JSON file is written atomically and keeps a `.bak` copy, and a damaged file is restored from it automatically; `auth.json` is the 0.2.x login, migrated once.

## Sign-in and roles
- Session cookie (`beacon_session`, signed with `secret.key`), scrypt password hashes in `users.json`. Roles: admin (everything), user (edit layouts and apps), viewer (view only). Guest = view-only profile with no sign-in, off by default, toggled in Settings > Users.
- Inactivity: sessions end after `idle_minutes` (default 10, Settings > Security, 0 = never) without real use. The page reports mouse/keyboard/touch with `POST /api/activity`; background polling (`GET /api/data`, `/api/servers`) does not count. Guests and "keep me signed in" sessions (`session["r"]`) are exempt. Expired requests get `401` with `expired: true`.
- Open routes: `/`, `/healthz`, `GET /api/me`, `GET /api/brand`, `POST /api/login`, `POST /api/setup`. Everything else needs a session; `PUT /api/dash` needs user+, other writes need admin. `max_attempts` (default 5) failed sign-ins per 5 minutes per client IP locks that IP out.
- Env: `UI_USER` (default admin) and `UI_PASSWORD` (always resets that user's password at start, creates the admin if missing); with neither, no account is created: `GET /api/me` returns `setup: true` and the page shows a setup form (`#sf`: name, email, password + confirm) that calls `POST /api/setup`, which creates the admin (email stored in `users.json`, not used for anything yet), signs them in, and answers 403 once any user exists. Whoever opens the page first creates the admin, so the README tells people to do it straight away. `UI_AUTH=off` removes sign-in entirely (proxy-side auth). `TRUST_PROXY=1` reads the client IP from X-Forwarded-For. `COOKIE_SECURE=1` over HTTPS (switches accept 1/true/yes/on). Responses carry CSP and nosniff headers.

## Feedback
Settings > Feedback (any signed-in role, not guests) builds a prefilled GitHub new-issue link and opens it in a new tab for the person to review and submit; nothing is sent from the server and no token is stored. The repository is `matt-waldeck/beacon` by default, overridable with `GITHUB_REPO` or by an admin in the Feedback page (`repo` in settings.json). The link uses `template=bug_report.yml|feature_request.yml`, `title`, and the forms' field ids (`what-happened`, `idea`, `diagnostics`); the forms live in `.github/ISSUE_TEMPLATE/` and must be committed to that repository. Diagnostics are opt-in and limited to version, browser, screen size and style. Planned upgrade: in-app submission through a GitHub App with device flow.

## Branding
`brand.json`: name, tab title, sign-in message, logo and favicon (stored as data URIs, validated server-side, 500 KB max). Edited in Settings > Branding; public read so the sign-in screen can use it. A blank logo or favicon means Beacon's own default: the artwork in `Images/` (icon.png, icon-white.png, favicon-48.png) is shrunk and embedded in index.html as the `LOGO_LT`, `LOGO_DK` and `FAV` data URIs, so the page stays one file and the Dockerfile needn't copy `Images/`. The logo has a light and a dark-surface variant, chosen in CSS by `--dl` (dark for the dark theme, system dark on auto, and Stark; light for Pastel). The `Beacon` name beside it is text from the brand name, so `Images/logo.png` (the full wordmark) isn't used in the app. If the artwork in `Images/` changes, re-embed it.

## Styles
Honeycrisp (default; Liquid Glass-inspired: wallpaper gradient, frosted tiles, floating capsule header; light/dark/auto), Pastel (candy colours, confetti and drifting bubbles, tiles that hop on hover, emoji tabs; light only), Stark (HUD, dark only). All CSS variables on `:root`, chosen in Settings > Appearance (per browser).

## Per-user cookie
`beacon_sort` (1 year) holds each user's list sorting as `{user: {devices|servers|apps: [column, direction]}}`; click a column header to sort, click again to flip. Default is by name, ascending.

## Appearance settings (per browser, localStorage)
`style` (honeycrisp | pastel | stark), `theme` (auto | light | dark; Honeycrisp only), `hover` (none | glow | bounce; unset = glow for Honeycrisp and Stark, bounce for Pastel), `fun` (Pastel only; off hides its emoji, sparkles and little animations), `bands`. They become `data-style`, `data-theme`, `data-hover`, `data-fun` on `<html>`. The selected tab is marked by one oval (`#pill`) that glides between tabs in every style, filled from the `--pill` token.

## History and storage
Device samples (`samples`: JSON in `data` plus numeric columns `m_cpu`…`m_poe`, filled by `save_sample`; `migrate()` adds and backfills them once, tracked with `PRAGMA user_version`) and server pings (`pings`) are kept raw for `retention()` days: Settings > Monitoring, then `retention_days` in config.json, then 7 (1 to 365). `prune()` runs every device cycle, so shortening it deletes at once. Ranges up to 24 hours are returned raw (thinned to roughly 300 points); longer ones are averaged in SQL into steps aligned across devices, with the newest real sample appended so facts stay current (pings carry `n` results, `d` no-replies, `max`). The page offers 15 min to 30 days, only as far as the retention covers, and remembers the choice. Settings > About shows storage (`GET /api/storage`, admin) with Clear icon cache, Compact database and Delete history (`POST /api/storage/purge`). Possible next steps: tiered retention (rollup tables kept longer than raw data), WAL mode.

## Dashboard model
- `dash.json` (v "1.0"): `{v, apps: {id: {name, url, icon}}, tabs: {home|network|servers|apps: [tile]}}`; only `home` holds tiles now (the other three are saved as empty lists). Tile: `{id, type, ref, x, y, w, h}` on a 12-column grid; `new: true` tiles are unsaved.
- Tile types: `stat`/`chart` (ref = key in `CAT` in index.html; the one stat with a per-tile setting is `n.net`, throughput, whose optional `mode` is `total` (default), `rx` or `tx`, chosen with the tile's gear in edit mode; it can be placed more than once; old `n.rx`/`n.tx` tiles are converted to it by `sane()`; the Network summary shows the total only), `summary`, `app` (Home only; an empty `ref` shows a menu in the tile to pick which app it shows; the Apps page is where apps are edited). To add a tracked value: a `CAT` entry plus a `STAT` or `CHART` function.
- On phones (under 700px) the grid becomes two stacked columns and layout editing is hidden. Lists are not tiles. Network and Servers = one fixed, non-configurable overview panel on top (`#ov`, built by `renderOv()` from the `OV` map in index.html: Network shows Devices online, Wireless clients (with the optional band split, offered only when some device reports bands) and total throughput beside a throughput chart; Servers shows Servers online, Average ping and Slowest ping beside a ping chart; no edit mode or Add tile there) and a scrollable list panel (`#lpanel`) filling the rest of the screen; rows expand for details and graphs, one at a time (opening a row closes the open one); add/edit/remove inline (admin). Servers have a type (`server` or `vm`, stored in `servers.json`). Apps = a list only, no grid: click a row to open the app, Edit (user+) for the form, Add to/Remove from Home; the catalog is `D.apps`; blank icon = Beacon looks the name up server-side in the collection chosen in Settings > About (`icon_source` in settings.json: `selfhst` = selfh.st, the default, CC BY 4.0, so credit is shown in Settings > About and the README; or `dashboard` = Dashboard Icons, Apache-2.0; both via jsDelivr, svg then png; Heimdall was dropped; the dropdown `#icsrc` sits with the storage figures, admin only; changing it clears the icon cache; `GET /api/me` returns `icons` so the page's CDN fallback matches), keeps a copy in `/data/icons`, and the add/edit form previews it and says where it came from; the browser falls back to the same CDN, then the first letter.
- Layout rule: tiles fall upward until they rest on another; the dragged tile is pinned.

## API
Open: `GET /healthz`, `GET /vendor/chart.umd.min.js`, `GET /api/me`, `GET /api/brand`, `POST /api/login`, `POST /api/setup` (first run only). Any signed-in role: `GET /api/data|servers|dash`, `POST /api/logout`, `POST /api/me/password`, `POST /api/activity`, `GET /api/icon?name=`. User+: `POST /api/icon/resolve`. User+: `PUT /api/dash`. Admin: `PUT /api/brand`, `POST /api/settings` (intervals, guest, idle_minutes, retention_days, icon_source, max_attempts), `GET`/`PUT /api/notify` (what is sent, batching and the list of destinations; webhook addresses and mail passwords are never returned, a blank one keeps the saved value for that id), `POST /api/notify/test` (send one message using one destination's unsaved values), `GET`/`PUT /api/unifi` (sites with status and no keys; PUT replaces sites and schedule, a blank key keeps the saved one), `POST /api/unifi/test` (try one site unsaved), `/api/unifi/discover` (check for new devices now; 409 if one is running), `/api/unifi/forget` (clear the removed-by-hand list), `GET|POST /api/users`, `PUT|DELETE /api/users/<name>`, `POST /api/<devices|servers>`, `PUT|DELETE /api/<devices|servers>/<name>`.

## UniFi API source
Official Integration API (`X-API-KEY`). Sites are set up in Settings > UniFi (`unifi.json`: id, name, url, key, site, verify); `UNIFI_URL` + `UNIFI_API_KEY` (+ `UNIFI_SITE`, `UNIFI_VERIFY_TLS`) add one more read-only site with id `env`. `unifi_sites()` is the merged list; none means pure SSH polling as before. `unifi_connect` probes `/proxy/network/integration` then `/integration` under the URL (UniFi OS consoles and standalone installs differ; the standalone path is unverified; UniFi OS Server's web UI port is 11443), resolves the site by id / `internalReference` / name, and caches `(base, site id, version, kind)` per site id (kind is inferred from the path that answered). Connection errors say where Beacon looked (`unreachable()`; a refused connection tells the user to use their UniFi OS Server's local web UI port). Each cycle `poll_unifi` goes through the sites in order; `unifi_read` lists devices, matches them to `devices.json` entries by IP (hostnames resolved), calls `statistics/latest` per matched device in the thread pool, and one filtered clients list (`type.eq('WIRELESS')`) counted by `uplinkDeviceId` for access points. The first site that knows a device wins. Per-site status is in `UF["state"][site id]` (ok, error, version, kind, devices, matched, last_ok; an error keeps the last good numbers) and is what `GET /api/unifi` shows. Samples use the same fields as SSH ones; `rx`/`tx` are the uplink rates (`RATE_MUL` = 1 assumes bits per second; the spec doesn't say, so check against the UniFi UI, use 8 if they are bytes); `clients` is wireless clients per AP. The API has no PoE watts or per-band counts, so `poe` and `bands` exist only on samples from the SSH path (an optional SSH extra for them was tried and removed: too much overhead on large networks). Devices no site lists fall through to `poll()` (SSH). On a controller error, devices that site answered for last cycle (`API_NAMES`: name -> site id) get an error sample and the rest use SSH. `/api/data` gives each device a `site` (the site that last answered for it, null if polled over SSH) and a top-level `sites` list of site names (empty unless there are two or more); with two or more, the Network list gets a Site column (head index 4, hidden by CSS unless the list has class `msite`) and a site filter select; the filter (`SITEF`, kept in localStorage) narrows the Network list and the Network overview (`DEVS()`), while Home stays network-wide. `mca()` is the shared mca-dump parser for the SSH path. The shared SSH login comes from `config.json` and `SSH_*` env vars only.

Device discovery: `discover()` lists every site's devices and appends those whose IP isn't in `devices.json` (name from the controller, `Name (ip)` on a clash; no address or an invalid one is skipped) unless the IP is in the removed-by-hand list (`ignore()` is called from `delete_item`, and lifted by `add_item` / `edit_item`); it returns `[{name, host, site}]` and per-site errors, which the manual check shows in a popup (`#cd`). `run_discovery()` (one at a time, `dlock`) stores `last_run` / `last_added` (names) / `last_errors` in `unifi.json`. The schedule (`discover`: enabled, mode `daily` at `HH:MM` server time or `hours`, default enabled daily 01:00) is driven by the `dloop` thread calling `dtick` every 30 s: with no `last_run` it only starts the clock (so the first automatic check is the next slot, not immediate); a missed daily slot is caught up; saving a changed schedule clears `last_run`. Server time follows `TZ`. The UI is Settings > UniFi (status cards with a neon pill per site, Configure… popup, Check for new devices now).

## Notifications
Settings > Notifications (admin; `notify.json`, 0600). Same shape as the UniFi page: a card with the event switches, then a list of destination cards (name, kind, On/Off/Failing light, where it goes, how the last message went) and a Configure… popup `#nd` (rows `.ds`, Add a webhook / Add an email, per-row Test and Remove, one Save that replaces the list; ids are generated, a blank secret keeps the saved one for the same id and kind, names are unique, up to 20). Events: `device` (network devices), `server` (servers and VMs), `unifi` (controllers), each a switch, plus `after` (failed checks in a row before reporting, default 3) and `batch` (0 = off, else 2 to 50: the number of messages arriving together at which they go out as one). Events, `after` and `batch` are saved by the card's own Save, the destinations by the popup's; `PUT /api/notify` takes any of the four and leaves the rest alone. Destinations: `webhook` (`generic` JSON, `discord`, `slack`, `ntfy`; the address is a secret, so only its host is shown back) and `email` through the user's own SMTP server (security `none`/`starttls`/`ssl`, optional login, From, up to 10 To addresses); each has `enabled` and a certificate-check switch. Every message goes to every enabled destination; events are global, not per destination. `notify_saved()` also reads the first version's file (one `webhook` and one `email` key) as two destinations with ids `webhook` and `email`.
`watch(kind, name, ok, why)` is called with every result (`save_sample`, `sloop`, `poll_unifi`) and keeps `NW[(kind, name)]`; after `after` failures in a row it queues one message, and one more when the check passes again, but only if the first was reported (`sent` is True; None means it was muted because that kind was switched off, so its recovery is muted too). `save_sample(..., notify=False)` is used for the error samples `poll_unifi` writes during a controller outage, so one controller outage is one message, not one per device. `notify_worker` drains `NQ` on its own thread, so a slow mail server never holds up checks. With batching on it waits `BATCH_WAIT` (15 s) after the first message, collects whatever else arrived, drops kinds that are switched off, and if at least `batch` remain sends one digest (`notify_digest`: title like "3 offline, 1 back online", lines grouped under Offline / Back online; the generic webhook gets `event: "digest"` and an `items` list) instead of separate messages; fewer than `batch` go out separately, so with batching on every message is delayed by up to `BATCH_WAIT`. Settings are read at send time (a switched-off kind or destination is skipped). `NLAST[destination id]` keeps how the last attempt went (memory only, shown on the page). `notify_prune` forgets removed devices, servers and sites. Not done: retries, per-destination event choices, metric thresholds.

## Conventions
Icon lookups happen only for names on the Apps page (`GET /api/icon` never fetches for an arbitrary name); a cached or fetched SVG is refused if it holds scripts, event handlers, embedded pages or entities, and icons are served with a sandboxing CSP. Numeric settings are clamped when read (`whole()`), so a damaged `settings.json` can't break requests. SSH host keys are pinned on first use (`TrustFirst` policy, `/data/known_hosts`, 0600; a changed key or a different key type for a known host is refused and shown as an error on the device; admins choose which to forget in Settings > Security > Forget SSH host keys…, a popup `#kd` listing each stored key by device name with an All checkbox: `GET /api/hostkeys` (admin) and `POST /api/hostkeys/forget {hosts: [...]}` or `{all: true}`). Failed password guesses are limited by `recent_fails`: sign-in per client IP, `POST /api/me/password` per user, both against the admin-set `max_attempts` (default 5, 1 to 20, Settings > Security, read with `GET /api/security`) within 5 minutes. The container starts as root only so `entrypoint.sh` can chown `/data`, then `gosu` runs Beacon as `beacon` (uid 10001); ping gets `cap_net_raw` as a file capability. Chart.js is pinned to 4.4.0 `chart.umd.js` by SHA-384 in the Dockerfile and in the page's CDN fallback. The Dockerfile makes `/app` world-readable after COPY (host file modes are carried into the image, and a private `app.py` crashed the first non-root build with PermissionError). The Docker pieces were written without a Docker daemon to test them.
Layouts sent to the server are validated (`clean_dash`) and cleaned again in the page (`sane()`), so a damaged `dash.json` can't break the UI. Status messages in Settings use `note()` and fade by themselves. Credentials never leave the server. Keep the code small; prefer patches to rewrites. Element ids in `index.html` must be unique (a clash between the sign-in password field and the list panel once hid every list). Check the UI in a real browser (headless Chromium via Playwright) rather than only syntax-checking it. Bind to loopback (`BIND_ADDR=127.0.0.1`) when a proxy on the same host fronts it.

## Tests
